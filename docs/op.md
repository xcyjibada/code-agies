举一个例子，经典，巧妙的利用看起来非常安全的点

我会避免给出能够直接复现攻击的利用步骤，但可以分析一些非常经典、非常有启发性的漏洞案例，重点放在思维模式而不是利用细节。

其中我最喜欢的一个案例类型是：

“安全检查做对了，但检查对象错了”

很多开发者会写出类似这样的逻辑：

用户输入
 ↓
安全检查
 ↓
后续使用

看起来完全正确。

问题是：

检查时看到的对象，和真正执行时使用的对象，不一定是同一个对象。

安全领域有个常见原则：

Check-Time ≠ Use-Time

（检查时刻不等于使用时刻）

一个抽象案例

假设系统允许用户下载文件：

用户请求
 ↓
检查文件是否位于允许目录
 ↓
打开文件
 ↓
返回内容

开发者认为：

只要路径在 uploads 目录下
就是安全的

于是实现：

1. 校验路径
2. 允许访问
3. 打开文件

逻辑没毛病。

研究员会问另一个问题：

检查完成后，这个对象会不会变化？

如果文件系统中的对象在检查后、打开前发生变化：

检查的是 A
使用的是 B

那么整个安全模型就崩了。

这里真正有价值的发现不是某个 API 调错了。

而是发现：

开发者假设：
检查结果永久有效

实际：
对象是动态变化的

这是很多高质量漏洞背后的核心思想。

第二个经典例子
“白名单是对的，但解释器不是同一个”

开发者：

只允许访问：
example.com

于是写：

if host == "example.com":
    allow

看起来严谨。

研究员不会立即测试绕过。

而是先问：

谁在解析 host？

可能有三个不同组件：

Web框架
 ↓
代理
 ↓
后端服务

每层都有自己的解析逻辑。

于是系统出现：

组件A认为：
host = example.com

组件B认为：
host = internal.service

每个组件单独看都没问题。

组合后出问题。

很多著名漏洞都属于：

Parser Differential（解析器差异）

即：

安全检查使用解析器A

实际执行使用解析器B
第三个案例（我认为最有代表性）
权限继承链

假设系统有：

团队
项目
文件

权限模型：

团队管理员
 ↓
项目管理员
 ↓
文件管理员

开发者写得很认真。

每个 API 都检查：

是否拥有权限

代码审计看不出问题。

研究员不看 API。

研究员画图：

创建团队
 ↓
邀请成员
 ↓
转移项目
 ↓
删除成员
 ↓
恢复项目

然后开始问：

如果这些动作以异常顺序组合呢？

最后可能发现：

正常流程：
A拥有项目

异常流程：
A转移项目
 ↓
权限缓存未刷新
 ↓
删除成员
 ↓
恢复对象
 ↓
仍保留旧权限

结果：

权限幽灵化

（Ghost Permission）

很多企业级产品都出现过这种问题。

为什么这些漏洞显得“巧妙”

因为它们都不是：

输入
 ↓
危险函数
 ↓
漏洞

而是：

系统假设
 ↓
发现假设
 ↓
构造状态
 ↓
打破假设

真正成熟的研究员看到代码时，经常先问：

系统相信什么？

例如：

路径不会变化
权限会同步
缓存一定正确
对象唯一
解析结果一致
用户身份稳定

然后问：

如果这个信念是错的呢？

这就是很多高质量 CVE 的来源。

所以我后来做审计时，一个习惯是：

看到安全代码先不高兴。

因为很多漏洞恰恰出现在：

代码写得很严谨
↓
所有人都相信它没问题
↓
没人继续质疑其前提

而高价值漏洞往往隐藏在这些“默认成立的前提条件”里面。真正值得训练的能力，不是找危险函数，而是识别系统里那些没人写出来、却被所有代码默认依赖的假设。

不，你举一个已有cve编号，符合上述条件的也就是看起来代码写的非常安全，连sink可达都不是，结果出现漏洞被申报cve的

有，而且我觉得最符合你说的“代码看起来非常安全，甚至不像 sink 可达问题”的经典案例，不是 Web 漏洞，而是几个文件系统相关 CVE。

其中我认为最值得研究的是：

CVE-2021-32803（node-tar）

这个漏洞我第一次读 patch 的时候印象非常深。

因为开发者实际上已经考虑了 symlink 攻击。

开发者的安全目标

node-tar 解压时明确要保证：

如果路径受到 symlink 影响
绝不解压

于是实现了一套保护：

解压目录
↓
检查目录是否为 symlink
↓
不是
↓
允许继续

从代码审计角度看：

source
↓
各种检查
↓
无危险sink

看起来已经结束了。

巧妙之处

为了性能优化。

作者加了一个缓存：

dirCache["a/b/c"] = true

含义：

这个目录已经确认存在
以后不用再 stat()

这是一个极其正常的优化。

甚至很多资深开发都会这么写。

安全假设

整个系统隐含了一个假设：

目录一旦检查过
以后还是那个目录

于是：

第一次检查
↓
目录安全
↓
加入缓存
↓
后续跳过检查

逻辑完全合理。

真正的问题

攻击者构造的不是：

恶意文件

而是：

目录
↓
同名symlink
↓
再来一个文件

某个时刻：

缓存认为：

foo 是目录

但真实文件系统里：

foo 已经不是目录
而是 symlink

了。

于是出现：

Cache State
      ≠
Filesystem State

这是漏洞根源。

为什么这个案例厉害

因为你审代码的时候会看到：

if (isSymbolicLink(path))
    throw Error()

然后觉得：

没戏了。

实际上漏洞不在这里。

漏洞在：

你什么时候决定不再检查？

换句话说。

漏洞不是：

检查失败

而是：

检查成功
↓
相信检查结果永远有效

这已经进入系统建模层面了。

第二个我特别喜欢的案例
CVE-2021-30465（runc）

这是容器安全历史上非常经典的案例。

很多研究员第一次看 patch：

看不懂为什么能逃逸

因为没有明显漏洞函数。

runc 的逻辑大概是：

验证挂载路径
↓
确认位于容器内
↓
执行 mount

开发者已经知道：

../../
symlink
traversal

这些问题。

因此写了很多检查。

问题在于：

检查时：

路径A

使用时：

路径B

攻击者利用文件系统对象变化导致：

Validated Path
      ≠
Mounted Path

最终突破容器边界。

但如果问我最震撼的案例

其实不是上面两个。

而是：

CVE-2021-21300（Git）

这个案例几乎没有传统意义上的漏洞代码。

开发者相信：

A != a

因为 Linux 文件系统如此。

于是：

A/
a/

是两个不同对象。

但在某些文件系统：

A == a

成立。

结果：

Git的逻辑视图
        ≠
文件系统的实际视图

攻击链最终导致克隆仓库时触发代码执行。

这个案例最有价值的地方在于：

你审 Git 代码时根本不会搜索：

exec(
system(
eval(

因为问题不在那里。

问题在：

程序员默认相信的世界

和

真实世界

不一致。

所以如果你想培养发现这种 CVE 的能力，我建议你以后看到这种代码不要高兴：

if safe(path) {
    proceed()
}

而是立刻问：

safe 对谁而言？

这个判断结果会过期吗？

有没有缓存？

有没有第二个解析器？

有没有第二个状态机？

有没有另一个组件看到的是不同对象？

我观察过不少高质量 CVE 作者的分析过程，他们很多时候不是沿着：

Source
↓
Sanitizer
↓
Sink

往下追。

而是在找：

Assumption
↓
Reality Mismatch
↓
State Divergence
↓
Security Impact

node-tar（CVE-2021-32803）和 Git（CVE-2021-21300）就是这种思维模式的教科书级案例。
