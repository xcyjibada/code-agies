## 架构组件

### Phase A: 路径发现（PathFinder）

**`agies/engine/v3/pathfinder/treesitter.py`** — tree-sitter 做源码级 source→sink 路径发现，替代 CodeQL 作为默认引擎（CodeQL 作为可选）。

- `TreeSitterPathFinder` — 遍历源文件 → 匹配 sink 模式 → 反向追溯 caller → 构建调用链
- `_build_call_graph` / `_resolve_call_recursive` — 递归 caller 解析（max_depth=10）
- 支持 7 类 sink 匹配（RCE/LFI/SSRF/SQLI/XSS/AFO/IDOR）

### Phase B: 路径排序

**`agies/engine/v3/slicer/sorter.py`** — 路径评分 + 去重 + Explore/Exploit 分配。

- `score_path()` — 5 维评分：source 类型、sink 危险度、调用深度、参数传播、信号权重
- `select_top_k()` — 阈值过滤 + 去重 + top-K 选择
- `is_anomalous()` — 异常路径检测（低分但高风险的 edge case）
- **Explore/Exploit 分离** — 5 个 Explore 槽位给低分但潜在高危的路径，防止评分模型的确认偏误

### Phase C: 漏洞专项 Prompt

**`agies/engine/v3/prompts/`** — 7 类 VulnHuntr 风格 prompt。

- 每类包含：sink 识别 + 攻击向量 + bypass 技术 + check list
- `get_prompt(vuln_type, code_block, readme_summary)` — 统一入口
- 重点设计：`lfi.py` 对 path-construction utility 的专项指导（posixpath.join 不是直接 sink，需要看消费者函数）

### Phase D: Intent Agent → Merge → Logic Agent

**`agies/engine/v3/agents/intent_agent.py`** — 对路径上的每个函数，LLM 提取开发者意图。

- `INTENT_PROMPT_TEMPLATE` — 输入源码 → 输出 intent/inputs/outputs/key_logic/suspicious/pass_through
- `_DANGEROUS_PATTERNS` — 硬编码危险函数模式列表，即使 LLM 说 "no" 也强制 pass_through
- `parse_intent_response()` — JSON 解析 + pass_through 启发式规则
- `pass_through=True` 时保留原始源码（不生成伪代码）

**`agies/engine/v3/agents/merge.py`** — 确定性排列。

- `MergeLayer.merge()` — 按函数顺序排列，dangerous 函数显示原始源码，safe 函数显示伪代码
- `MergeLayer.check_coherence()` — 一致性检查（函数数量、intent/key_logic 完整性）

**`agies/engine/v3/agents/logic_agent.py`** — 矛盾检测。

- `prepare_prompt()` — 用 `get_prompt()` 加载对应漏洞类型的 VulnHuntr prompt
- `parse_logic_response()` — 解析 contradictions JSON + 兼容 VulnHuntr 输出格式
- `run()` → `AgentPhaseResult`（contradictions、confidence、is_vulnerable）
- **Verification 步骤**：`create_verify_prompt()` → `verify()` — skeptial reviewer 二次验证，被拒时降级 confidence

### Aggregator

**`agies/engine/v3/aggregator/blackboard.py`** — 跨路径知识黑板。

- `Blackboard` — 缓存 Intent 分析结果 + 跨路径知识注入
- `record_knowledge()` / `query_knowledge()` — 函数级别的知识记录和查询

### 编排器

**`agies/engine/v3/runner.py`** — 主流程编排（631 行）。

`run_v3()` 完整链路：
1. Tree-sitter 源码解析
2. 7 类 sink pattern 扫描
3. 调用链发现（反向追溯 caller）
4. 路径评分 + top-K 选择
5. Code block 构建（含 alias 检测 + companion methods）
6. Intent Agent 池（并行分析路径上的所有函数）
7. Merge 排列
8. Logic Agent 矛盾检测
9. Verification（高置信发现）
10. 结果聚合输出

## 设计决策

### Pass_through 模式

Intent Agent 输出 `pass_through: yes/no`：
- `yes` → Merge 保留原始源码，Logic Agent 看到真实代码
- `no` → Merge 输出伪代码，Logic Agent 做逻辑谬误分析

危险函数硬编码列表（即使 LLM 误判也强制 pass_through）：
```
posixpath.join, ntpath.join, os.path.join,
PurePosixPath, PureWindowsPath, pathlib.PurePosixPath,
subprocess.*, popen, os.system, __import__, compile
```

### Verification 阈值

第一次实现（太激进）→ 第二次调整：
- 激进版：`not confirmed OR v_confidence < 5` → 误杀真实发现
- 当前版：`not confirmed AND v_confidence < 4` → 只有明确拒绝+低置信才降级

### Explore/Exploit 分离

原因：评分模型的确认偏误导致非标准 sink 被结构性过滤。
- Exploit: 前 K 个高分的路径 → 确定性分析
- Explore: 5 个槽位 → 低分但异常的路径 → 避免盲区

## 今日问题记录

### 已解决

#### 1. posixpath.join 被错误分类为 AFO

- **发现**：跑 zipp BountyBench，LLM 对 joinpath 报 0/10 分。DeepSeek 说"这个函数不写文件"。
- **根因**：`sink_patterns.py` 中 `posixpath.join`、`PurePosixPath` 等路径构造工具被标记为 AFO（Arbitrary File Overwrite）。
- **影响**：AFO prompt 问 "sink 是否写文件" → LLM 答否 → 0/10 分。路径穿越检测完全失效。
- **修复**：所有 path-construction utility 由 AFO → LFI。同步更新 LFI prompt 加入路径构造 → 消费者函数分析指导。
- **教训**：sink 分类直接影响 prompt 模板选择 → 分类错则不可能找对漏洞。分类不是简单标签映射，需要理解语义（工具函数 vs 直接 sink）。

#### 2. Intent Agent 被绕过（逻辑短路）

- **发现**：用户问"按理来说v3后面都是伪代码，应该只是逻辑谬误有效？为什么还能找到某个函数有错误？" → 排查发现 Logic Agent 从未收到伪代码。
- **根因**：`logic_agent.py:prepare_prompt()` 中 `code_block or intent_chain` — `code_block`（LLM 构建的 code_block）始终非空字符串，所以 `intent_chain` 永远不生效。Python 的 `or` 短路导致整个 Intent→Merge 阶段白跑。
- **影响**：Logic Agent 直接看源码，伪代码矛盾分析从未执行 → Pass_through 设计没有实际意义。
- **修复**：分开传入 `code_block` 和 `intent_chain`，Logic Agent 明确使用 intent_chain。
- **教训**：一行 `or` 短路就能让整个流水线白跑。用户比我先发现问题（"你是不是改了我的intentAgent，把他去掉了？"），说明我写代码后需要端到端验证数据流是否真的按设计流动。

#### 3. `__truediv__` alias 未被 tree-sitter 追踪

- **发现**：跑 zipp 时 path finder 找到的 joinpath 调用者全是测试函数，真正的 `Path.__truediv__`（重载 `/` 运算符的生产入口）不在调用链中。
- **根因**：`__truediv__ = joinpath` 是类级别的别名赋值，tree-sitter call graph 只追踪显式函数调用，不追踪赋值引用。
- **影响**：关键调用链断裂，Logic Agent 只看到测试代码，错过真正攻击面。
- **修复**：`_find_function_aliases()` — 扫描源文件，正则匹配 `alias = func_name`（以及类内 `def alias(self): return func_name(...)`），在 code_block 中标注 alias 关系。
- **教训**：静态分析工具（tree-sitter）有固有盲区。生产环境的别名使用（Python 的 `__truediv__ = joinpath`、JavaScript 的 `module.exports = fn`）需要额外的启发式层补偿。

#### 4. Path-builder sink 缺少消费者上下文

- **发现**：Logic Agent 拿到 joinpath 源码（2 行，调 `os.path.join`）后，LLM 无法判断危险性 — "这只是个路径工具函数"。
- **根因**：Path-builder（joinpath）本身不执行 I/O，危险的是调用它的消费者（read_text、open、extractall）。但 LLM 只看单个函数，看不到消费者。
- **影响**：joinpath 始终被 LLM 判定为 "safe utility"，即使它是 zipp CVE-2024-5569 的核心入口。
- **修复**：`_find_companion_methods()` — 用 AST 找到 sink 所在类，提取所有消费者方法，和 sink 代码一并放入 code_block。例如 joinpath 和 read_text、read_bytes、open 一起发给 LLM。
- **引发的问题**："需要消费函数才能确定危险函数的危险性吗？" → 讨论了 sink-type 漏洞（RCE/SSRF 有直接危险 sink）vs data-flow 漏洞（Path Traversal 的 sink 是工具函数，需要配对消费者）。结论：后者需要 companion methods，前者不需要。
- **教训**：不是所有漏洞类型都是"找危险函数"那么简单。Path Traversal 是 path-builder + read/write 的组合漏洞。

#### 5. Verification 步骤阈值过严

- **发现**：第一次验证逻辑用 `not confirmed OR v_confidence < 5`，大量真实发现被拒。
- **根因**：prompt 太激进（"be critical"），阈值太低。
- **修复**：prompt 改为 "focus on technical feasibility"，阈值改为 `not confirmed AND v_confidence < 4`（只有明确拒绝+低置信才降级）。
- **教训**：验证的 prompt phrasing 直接影响误杀率。验证的目的是过滤明显误报，不是找茬。

#### 6. v3 跑 zipp 结果不如 v2

- **发现**：用户反馈"再次跑zipp的结果还不如上次吗？"。
- **分析**：两个原因叠加：① 当时 sink 分类还是 AFO（全部 0/10）；② DeepSeek 偶发输出 "unknown" 或空结果。
- **修复**：修复 sink 分类后重新测试，最佳结果 joinpath 8/10、read_bytes 8/10、_base 8/10。但依然不稳定（见未解决问题 #1）。
- **教训**：v3 的伪代码+矛盾分析设计不差，但"给 LLM 看什么代码"比"用什么 prompt"影响更大。

### 未解决

#### 1. DeepSeek 非确定性（最严重）

- **现象**：temperature=0 下每次跑结果不同。有时 3 个 vulnerable 发现，有时 0。输出格式也不一致（有时 "unknown"，有时返回空 JSON）。
- **根因猜测**：DeepSeek API 的 temperature=0 可能不是真正的 0（API 层有随机性）。或者 prompt 中的代码上下文差异触发了不同推理路径。
- **影响**：无法稳定复现检测。CI 不可靠，无法做回归测试。
- **尝试**：用 Claude Sonnet 4.6 替换测试（见未解决问题 #2）。
- **优先级**：高 — 非确定性使整个管线的输出不可信。

#### 2. LLM Library Bias

- **现象**：DeepSeek 持续拒绝将库函数标记为脆弱（"this is library code, not application code"）。
- **影响**：zipp 是标准库 `zipfile` 的封装，joinpath 等函数被 LLM 判定为"安全的标准库用法"。
- **本质问题**：库代码的漏洞通常不在函数内部（代码自洽），而在调用方使用不当（跨边界共识违反）。Intent Agent "函数的代码实现了它的意图" → 判断为安全。但漏洞在 caller 使用 path-builder 拼接未清洗的用户输入。
- **当前缓解**：Pass_through 模式让 Logic Agent 看到源码 + companion methods，让 LLM 判断组合风险；硬编码危险函数列表强制 pass_through。
- **优先级**：高 — 这是 SAST 工具 vs LLM 的固有矛盾：LLM 倾向于看单函数自洽性，漏洞往往是跨边界的。

#### 3. teio.me 中转站无法使用

- **现象**：两个 key 均无效 — `sk-ulNdy...` → "Invalid token"；`sk-JA55s...` → 所有模型 403。
- **尝试**：测试了 12+ 种 model name 变体，均返回 403/model_not_found。
- **影响**：无法用 Claude Sonnet 4.6 做交叉验证，无法判断非确定性问题来自 DeepSeek 还是架构。
- **结论**：key 余额为 0 或已过期。需要新 key。

#### 4. joinpath 检测不稳定

- **现象**：即使修复了 sink 分类、companion methods、alias 追踪，LLM 有时仍然说 "library code is not vulnerable"。
- **分析**：和 #1、#2 同根 — LLM 非确定性 + library bias。同样的代码块、同样的 prompt，不同 run 结果不同。
- **影响**：CVE-2024-5569 的检测成功率 ~50%（3/6 runs 成功）。
- **优先级**：中 — 架构设计已经完善修复，剩下的需要更强的 LLM 或更好的 prompt design。
